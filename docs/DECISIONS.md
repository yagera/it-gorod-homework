# DECISIONS

Короткие записи: дата, решение, причина, альтернативы. Нумерация: записи 1–5 — решения по скелету, 6 — ограничения explorer, 7 — выводы EDA T1.

## 1. 2026-11-19 — Без Hydra, MLflow, DVC, Docker
- **Решение:** конфиги — YAML → dataclass через pyyaml; трекинг экспериментов — `docs/EXPERIMENTS.md`; воспроизводимость — `uv.lock` и seed=42; точка входа — один CLI и Makefile.
- **Причина:** два небольших задания, один исполнитель, три дня до дедлайна, сдача — два CSV. Данные выданы локально и не версионируются. Инфраструктура съела бы время без выигрыша в метрике.
- **Альтернативы:** Hydra (конфиги), MLflow (трекинг), DVC (версии данных), Docker (окружение) — каждая закрывает то, что здесь уже закрыто проще.

## 2. 2026-11-19 — Правило утечки T1 = A, фолды expanding window
- **Решение:** для года Y можно использовать все признаки года Y и любые данные лет < Y (включая лаги таргета); нельзя — таргет года Y и любые данные лет > Y. Валидация T1 только по времени: фолды ≤2021→2022 и ≤2022→2023 (`configs/t1.yaml`, `split.folds`), тест утечек идёт по каждому фолду.
- **Причина:** в test даны признаки 2024 года (наём, отклики и т.д.) — это ровно та информация, которая будет доступна при сдаче.
- **Альтернатива (B):** из года Y только известное на его начало. Безопаснее концептуально, но отбрасывает сильные признаки, которые в test всё равно есть, и ухудшает MAPE.

## 3. 2026-11-19 — Единый CLI `itgorod`
- **Решение:** подкоманды `t1`, `t2`, `validate`, `check-time-split`; Makefile — тонкие обёртки. Проверки — обычные функции в `itgorod/validation.py`: их вызывают pytest, скиллы, CI и CLI.
- **Альтернативы:** отдельные скрипты в `scripts/` (проверки расползаются копиями, хуже тестируются); ноутбуки + nbconvert (плохо тестируются и ложатся на ruff/CI) — ноутбуки только для EDA.

## 4. 2026-11-19 — Схема валидации T2: TBD
- **Решение:** не фиксировать (ни в AGENTS.md, ни в конфиге), пока не проверено, разбит ли test по времени относительно train (дата в шапке документа). Правило будет записано сюда и в AGENTS.md после проверки.
- **Причина:** выбор между stratified и временным разбиением зависит от этого факта, а проверка требует прохода по текстам — это этап T2.

## 5. 2026-11-19 — Тяжёлые зависимости в группе `dl`, CI минимальный
- **Решение:** torch, transformers, sentence-transformers, catboost, lightgbm — в `[dependency-groups] dl`; `default-groups = ["dev", "dl"]` (локально `uv sync` ставит всё); CI: `uv sync --frozen --no-group dl`. Один workflow (ruff, pytest, gitleaks), без torch и без реальных данных.
- **Причина:** в `uv.lock` десятки CUDA-пакетов (`nvidia-*`), несколько ГБ на каждый push; скелет их не использует.
- **Если CI станет дорогим по времени:** отключаем; основная проверка — локально (`make ci`, pre-commit).
- **Альтернатива:** не трогать `pyproject.toml` и исключать пакеты флагами `--no-install-package` в CI — хрупко: новая тяжёлая зависимость тихо попала бы в CI.
- **Ещё:** `gitleaks-action` закреплён на `@v2` (по спеке); `v3` уже вышел, поведение не проверялось.

## 6. 2026-11-19 — Ограничения субагента explorer держатся на контракте в промпте

- **Решение:** `explorer` (haiku) имеет `tools: Read, Grep, Glob, Bash`. Запреты (не писать, не править и не удалять файлы в репо, не `rm`/`mv`, не `git commit`, не `git push`, не читать `.env*`, не грузить `text` T2 целиком) записаны **только текстом контракта** в `.claude/agents/explorer.md`. Технически Bash у него открыт.
- **Остаточный риск принят:** Bash нельзя закрыть полностью (интерпретатор, перенаправление), а модель может нарушить контракт. Последствия ограничены: данные в `data/` вне git и восстановимы из выдачи, код под git, коммитить explorer не может без согласия.
- **Что закрыто технически:** `git push` запрещён глобально в `.claude/settings.json` (`permissions.deny`), как и чтение `.env*`. Коммит делает только основная сессия по команде «коммить».
- **Почему так:** первая версия с `disallowedTools: Bash(rm:*), Bash(mv:*), Bash(git commit:*), Bash(git push:*), Write, Edit` во frontmatter привела к тому, что агент при запуске получил только `Read, Grep, Glob` — без Bash, то есть разведка parquet через pyarrow стала невозможной. Причину не выяснял (предположение: `disallowedTools` с шаблонами Bash повлиял на выдачу инструментов).
- **Альтернативы:** оставить `disallowedTools` (explorer без Bash — бесполезен для разведки); глобальные deny на `rm`/`mv`/`git commit` в `settings.json` (мешают основной сессии, которая коммитит по команде).
- **Проверка (повторная проба после перезагрузки агентов):** `uv run python -I -c "import pyarrow"` выполнен (pyarrow 26.0.1); `rm` тестового файла в scratchpad агент отказался выполнять по контракту, файл цел. Это проверка послушности контракту, а не технического запрета: Bash открыт. В списке инструментов агент назвал `Read`, `Bash`, `SubagentHandback` (`Grep`/`Glob` не перечислил — на разведку не влияет).

## 7. 2026-11-19 — EDA T1: выводы и решения по признакам, пропускам, выбросам

Источник: `notebooks/01_t1_eda.py` (функции — `src/itgorod/eda.py`, графики — `docs/figures/t1_*.png`). Цифры — train 2020–2023 (505 отделов × 4 года), test — 2024. MAPE ниже — диагностика гипотез по временным фолдам (≤2021→2022, ≤2022→2023), **не бейзлайн** (в `EXPERIMENTS.md` не заносится).

1. **Пропуски и дубли.** В train 2021 строка: одна полностью пустая (`read_t1` её удаляет), других строк без `department_id`/`year` нет, дублей пары (отдел, год) нет, все 505 id test есть в train. Пропуск хотя бы в одном поле — 66 из 2020 строк (3,3%): `inbound_applications` 36 (из них 32 в 2020), `total_salary_budget` 26, `devs_fired` 22, `devs_hired` 20, `share_seniors` 18, `avg_dev_salary` 17, `current_staff_count`/`turnover_rate` по 15. Таргет и `active_projects_count` пропущены в одних и тех же 7 строках. В test пропуски только в 7 колонках (≤5 строк на колонку), `active_projects_count` и `inbound_applications` без пропусков. **Решение:** строки без таргета в обучение не берём (по ним можно считать лишь признаки); пропуски признаков сначала восстанавливаем точными тождествами `total_salary_budget = 1,2 × current_staff_count × avg_dev_salary` (отношение 1,2000 ± 0,0005) и `turnover_rate = (devs_hired + devs_fired) / current_staff_count` (1,0000 ± 0,000002), остаток — NaN для градиентного бустинга или медиана, считанная по train-годам фолда (правило A).
2. **Нули `inbound_applications` и выбросы.** Нулей 53 (2020: 0, 2021: 26, 2022: 15, 2023: 12), в 2020 вместо них 32 NaN; в test 5 нулей. Таргет в этих строках обычный (среднее 2200 против 2111), поэтому 0 — скорее маркер пропуска, а не «нет заявок». **Решение:** считать 0 пропуском плюс флаг `inbound_missing`. Выбросы `inbound_applications`: 17 226 и 16 859 при медиане 567 и p99 2474 (2 строки) — не удаляем, используем log1p. `turnover_rate > 1`: 11 строк в 7 отделах (отдел 1000047 — все 4 года, 1,28–1,56). Это не ошибка данных: по тождеству из п. 1 при `devs_hired + devs_fired > staff` оборот > 1. **Решение:** не клипуем и не удаляем.
3. **Таргет и MAPE.** Правосторонний (skew 1,22; для log — −1,19), среднее растёт 1983 → 2087 → 2161 → 2202 (+5,2% / +3,6% / +1,9% год к году, рост замедляется), min 41, max 9458. Значений < 200 всего 32 (1,6% строк), но на них приходится 16,5% суммарного веса 1/y, то есть MAPE к ним чувствителен. **Решение:** моделировать в относительной шкале (log таргета или ratio, п. 4), без `clip` снизу; метрику считать по фолдам и отдельно по строкам y < 200.
4. **Главная структура: `yearly_cv_processed ≈ ratio_отдела × active_projects_count`.** Spearman таргета с `active_projects_count` 0,972 (со `current_staff_count` 0,941, с `total_salary_budget` 0,939). Внутри отдела ratio стабилен: медианный CV 2,3%, 99% строк в пределах ±13,5% от медианы отдела; строк с отклонением > 15% всего 17 (9 из них в 2020, у части малые `active_projects_count`, например 2 и 5). Между отделами ratio разный (std 4,1 при среднем 25,5), а `tech_stack` его почти не объясняет: средние по стекам 24,5–26,3, MAPE «ratio по стеку × проекты» 15,4%. Сдвиг ratio по годам мал (среднее 25,2 → 25,6), тренд внутри отдела ≈ +0,14 в год при разбросе ±0,6. MAPE по фолдам (2022 / 2023, на общих строках; число строк печатает ноутбук): ratio отдела по последнему году × проекты — 2,8% / 3,0%; по среднему за train-годы — 3,5% / 3,5%; наивный лаг таргета — 4,4% / 6,2%. **Решение:** основная модель — прогноз ratio (или log ratio) отдела с умножением на `active_projects_count` 2024; признаки отдела — последний и средний ratio по train-годам, его тренд. Лаг таргета без ratio не берём как основу.
5. **Другие признаки: формулы для таргета нет.** Точные тождества есть только между самими признаками (п. 1). По одиночке `inbound_applications` ρ = 0,85, `tech_brand_rating` 0,63, `devs_fired`/`devs_hired` 0,62/0,59, `avg_dev_salary` 0,37 (лог-линейная модель на одном признаке даёт MAPE ≥ 15% против 3% у ratio-подхода). Связь остатка (ratio) с `devs_hired`/`devs_fired` слабая (ρ 0,17 / 0,08), с `inbound_applications`, `avg_dev_salary`, `tech_brand_rating` — 0,35 / 0,36 / 0,31 (вероятно, межотдельный эффект). **Решение:** берём `active_projects_count` (ядро), `current_staff_count`, `total_salary_budget` и `avg_dev_salary` (оба в относительном виде, п. 6), `inbound_applications` (log1p + флаг), `tech_brand_rating`, `tech_stack` и лаги ratio; `devs_hired`, `devs_fired`, `turnover_rate`, `share_seniors` — кандидаты, оставляем только если улучшают временной CV.
6. **Сдвиг train 2023 → test 2024.** Ключевые признаки стабильны: `active_projects_count` −0,2% (KS 0,03), `current_staff_count` −0,6% (KS 0,02), `tech_brand_rating` −1,7%. Сдвинулись `avg_dev_salary` +8,6% (KS 0,29, p ≈ 0; сдвиг 0,74 std — единственный сильный), `devs_fired` +16,7% (KS 0,13, p = 0,0003), `devs_hired` −11,4% (KS 0,07, незначимо), `share_seniors` +4,5% (KS 0,09), `total_salary_budget` +8,0% (следствие зарплаты по тождеству). **Решение:** `avg_dev_salary` и `total_salary_budget` подаём только в относительном виде (отношение к значению того же отдела за прошлый год или к его среднему по train-годам), не в абсолюте; тождество с зарплатой используем лишь для восстановления пропусков. Дрейф между train-годами не измерялся — для этих признаков решает временной CV.
7. **`tech_stack` и покрытие отделов.** У всех 505 отделов ровно один стек за все годы, 15 значений (26–45 отделов в каждом), стек в test совпадает с train у 100% отделов. Все отделы test есть в train, поэтому история отдела (лаги, ratio) доступна для каждой строки 2024. **Решение:** `tech_stack` — категориальный признак уровня отдела; сам по себе он слабый (п. 4), поэтому агрегаты по стеку считать только по train-годам фолда; основная информация — в `department_id`-истории.

## Известные ограничения скелета

Найдены ревью ветки `scaffold` (агент `reviewer`), осознанно оставлены без правок — не влияют на форму сдачи (два CSV), которую проверяет `make validate`. Вернуться, если соответствующий код начнёт использоваться всерьёз.

- **`run_t1` и `run_t2_smoke` не проверяют собственный результат.** При необычных входных данных (нет ни одного таргета в году `target_year-1`, id из sample отсутствует в test) в CSV могут попасть NaN или нули, а CLI всё равно напишет «written». Страховка — отдельный шаг `make validate` и Definition of Done.
- **Ключ кэша T2 не включает источник.** В имени кэша есть `max_chars` и число строк smoke, но нет пути или mtime исходного parquet; запись кэша неатомарна. Смена `paths.train`/`paths.test` или перевыдача файла требует `--force`; прерванная запись оставляет битый файл (при чтении упадёт, а не пересоберётся).
- **Ключ конфига `placeholder.fallback` не используется:** цепочка фолбэков зашита в `t1.py`. Менять ключ бесполезно. Уберём или подключим при замене плейсхолдера настоящим бейзлайном.
- **Дубль пары (`department_id`, `year`) в train** даёт непонятную `InvalidIndexError` в `predict_placeholder` (`Series.map`). В выданных данных дублей нет (проверено разведкой).
- **`check-time-split` не проверяет, что все строки test относятся к `target_year`.** Выданный test целиком 2024; другая версия файла не будет замечена.
- **Smoke T2 обучается на первых N строках parquet.** Если файл отсортирован по `code` или N мал, может попасть один класс, и LogisticRegression упадёт с `ValueError`. Сейчас первые 5000 строк покрывают 56 из 58 классов.
- **Базы относительных путей разные:** `--config` и пути из конфига считаются от корня репозитория, а CSV-аргумент `itgorod validate` — от текущей папки. Запускать из корня репо.
